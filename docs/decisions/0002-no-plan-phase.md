# 0002. ティックに PLAN フェーズを置く

- 日付: 2026-09-07
- 状態: 却下

## 何を決めたか

DECIDE と ACT の間に PLAN フェーズを置き、Goal から作った実装計画を state として持ち越す案を
却下する。ティックの構造も、DECIDE が選べる行動の集合も変えない。DB に計画の層も足さない。

案が解こうとしていた問題——実装役が毎ティック新しいセッションで走るため、前のティックの
Actor が何を考えたかが次のティックに残らない——は実在する。**持ち越すものを計画から
試行の記録に変えて解く。** 方向は2つで、どちらも形はまだ決めていない。

- **Actor の試行台帳を持つ。** 正本は DB に置き、worktree には毎ティック再生成する
  上限付きのビューだけを置く。Actor の最終メッセージは主張であって Fact ではないと、
  ビューの側に明示する
- **ループ検知を二系統にする。** いまの `digestOf`（`src/domain/digest.ts`）は Fact の
  `key=value@confidence` しか見ておらず、失敗したコマンドの出力が入っていない。
  同じ失敗を繰り返しても観測は動かないので、詰まりの判定が両方向に外れる

## なぜそう決めたか

**却下の半分は既に決まっていた。** §10-12 は `Plan / Task` テーブルを**作らないと決めた**。
§4.5 はそれを表に写し、この層だけは「まだ作っていない」ではないと断ったうえで、
「`REPLAN` は残るが、その結果を DB の別の層には持たない」と書いている。
今回新しいのは、DB の層ではなくティックのフェーズとして置く形になる。
以下の3つは、その新しい部分に対する理由になる。

**1. 要るのは将来の処方箋ではなく、過去の試行の記録になる。** 実際に困っているのは
「何を試して駄目だったか」が消えることだ。Plan（これからどうするか）を置いても、
その枠は試行の記録で埋まる。器の名前と中身が食い違ったまま増えていく。
**これは設計から出る理由ではなく、回して分かったことになる。**照らす節が無いので、
却下そのものを支えるのは下の2つになる。

**2. Plan は陳腐化する。** コードが動いたあとの Plan は嘘になりうる。ent は Fact ですら
持ち越しを許していない。§10-11 は `local.dirty` について「読むのは今ティックの OBSERVE が
作った Fact だけにする」と決めている。理由は、前ティックの値を今の観測として読むと
「確かめられなかった」が「汚れている」に化けるからになる。**いま正しいことにして
持ち越したテキストが、次のティックで嘘になる形は採らない。**

**却下しているのは処方箋の持ち越しであって、テキストの持ち越し一般ではない。**
代わりに置く試行台帳が持つのは過去形の記録で、「commit X を読んだ Actor がこう述べた」は
あとから変わらない（§4.3 が同じ線を引いている）。「これからこう直す」は変わる。

**3. `src/domain/action.ts` が「`PLAN → ACT → VERIFY` を固定の workflow にしない」と
宣言している。** §1 の図の但し書きも同じことを書き、`REPLAN` を分岐先の一つに数えている。
Plan を state として持つと、controller が Gap の埋め方ではなく手順を持つことになる。

### 却下の理由として挙げたが、成立しなかったもの

検討の途中で次の2つを却下理由に挙げた。どちらもドキュメントの誤読で、**同じ誤読を
もう一度しないために残す。**

**「検証できないテキストを持ち越すのは §3.1 と衝突する」——成立しない。** §3.1 は
INFERRED を「LLM の推論やコード読解。**Plan の材料には使ってよいが**、Goal を COMPLETED に
する判定には使わない」と書いている。禁じているのは完了判定への流用だけで、検証できない
テキストを持つこと自体は禁じていない。上の理由2が §3.1 ではなく §10-11 を引くのは、
持ち越しを止めているのが信頼度の規約ではなく観測の規約だからになる。

**「計画は既に `.goals/<id>.yaml` の `desired_state` にある」——成立しない。** §1 は
「人間が書くのは『どうなってほしいか』だけで、Goal 内のタスク分解、Actor role の選択、
**実装手順は controller が決める**」と分担を書いている。`desired_state` は end state であって
計画ではない。「もうある」ではなく「controller の側にしか無い」が正しい。

**§3.1 と §10-11 は直していない。** 却下の根拠は現在の文面のまま揃っており、§3.1 も
書かれているとおりで正しい。誤っていたのは読み方だけになる。

**§5 だけは直した。** MVP に「入れる」側が `ASSESS、PLAN / REPLAN、DECIDE` と並べ、
§3.5 がそれを「ティック内の `PLAN / REPLAN` の段」と名指ししていた。**却下した当のものが
「入れる」欄に残っていた**ことになる。§1 の図の但し書きとも §4.5 とも合わないので、
ティック内の `PLAN` を落とし、§3.5 の指す先をこの判断に差し替えた（英語版・日本語版の両方）。
`docs/decisions/README.md` が「design.md の側を直すべきだと分かったら、ここには書かず
design.md を直す」と決めているのに従う。

## 代わりに検討して落とした案

無し。案は1つで、比べたのは「入れる」と「入れない」になる。

## 効いてくる範囲

- **DECIDE の行動集合**（`src/domain/action.ts`）: `PLAN` を足さない。LLM が選べるのは
  `ACT` / `VERIFY` / `WAIT` / `REPLAN` のままになる
- **データモデル**（§4.5）: `Plan / Task` を作らない方針を変えない
- **`REPLAN`**: 受け手が無いまま残る。`nextStatus` が `ACTIVE` を返すだけで
  （`src/domain/goal-state.ts`）、選んでも次のティックに何も渡らない。**この判断は
  そこを埋めない。** 埋める経路は §10-12 が既に置いていて、ループを回している最中に
  planner が `.goals/*.yaml` を書き換える側になる。試行台帳はその代わりではない
- **試行台帳とループ検知の二系統**: ここで決めたのは向きだけで、置き場と形はどちらも
  決めていない。具体案が出た時点で、オーナーの6つの問いをもう一度通す
