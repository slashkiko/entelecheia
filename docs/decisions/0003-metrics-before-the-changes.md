# 0003. 収束の指標は7つに割り、2つの変更より先に固定する

- 日付: 2026-09-07
- 状態: 採用

## 何を決めたか

ent の収束を測る指標を7つに割り、定義と基準線を `docs/metrics.md` に置いた。
ループ検知の二系統化と Actor の試行台帳より先に固定するので、入れたものを正当化する指標を
後から選べない。7つのうち4つはいまの出力で測れ、1つは集計を足せば出せ、
2つは観測が無い。観測が無い2つは空欄のまま残す。

## なぜそう決めたか

**1本の指標は自分で殺せる。** 「`loop_detected` で人間が呼ばれた回数」だけを見るなら、
検知を弱めれば改善に見える。減った分は `budget_exhausted` と無駄な Actor 起動へ移るので、
1本ではその移動が見えない。互いの逃げ道を塞ぐ形で割る必要がある。

**人間介入は理由別にしか読めない。** 基準線の介入7件のうち4件は
`ESCALATE(protected_path_touched)` で、ループ検知とも試行台帳とも関係がない。総数で見ると、
この4件の増減に測りたい変化が埋もれる。`src/usecase/inspect.ts:77` が停止理由を
種別と理由の組で持つのは、この2つを見分けるためになる。1本の文字列に畳むと、
`ESCALATE(protected_path_touched)` と `WAIT(human_review_pending)` が同じ見た目になる。

**基準線を先に測ったのは、`loop_detected` が一度も出ていないと分かったからになる。**
実データ7本の判断19件に `ESCALATE(loop_detected)` と `ESCALATE(budget_exhausted)` は0件で、
発火したのは `protected_path_touched` の4件だけになる。ループ検知の変更には過去の基準線が
無く、履歴での前後比較ができない。指標を決める前にこれを知らないと、測れない比較を
前提にした計画を書くことになる。

design.md §10-2「上限値の初期チューニング」が、この測定結果を待っている論点になる。
`max_unchanged_reconciles` を含む上限は仮置きのままで、基準線が無いと動かせない。

## 代わりに検討して落とした案

**`loop_detected` の介入回数1本。** 却下した。上記のとおり、検知を弱めるだけで改善に見える。

**人間介入の総数1本。** 却下した。`protected_path_touched` が支配していて、
測りたい2つの変更と無関係な増減で数字が動く。

**指標の定義を `docs/decisions/` に置く。** 却下した。判断ログは判定が終われば動かないが、
指標の定義は動く。観測が足されれば分類が変わり、基準線は測るたびに増える。
判定の記録と混ぜると、決定が後から書き換わったように見える。定義は `docs/metrics.md` に置き、
判定であるこの文書だけをここに残した。

**過去の失敗時点をリプレイして A/B を取る。** ループ検知については却下した。
`guard_base_sha` は7本すべて git から到達でき、宣言も生ログも残っているので材料はある。
しかし `loop_detected` が0回なので、再現すべき失敗点が1つも存在しない。試行台帳については
種が2本（同じ Goal 内で ACT を2ティック続けた例）あるので、補助として残した。
主たる比較は前向きに各アーム10本で取る。

## 効いてくる範囲

- `docs/metrics.md` — 指標の定義、基準線、測れるかの検証、比較の取り方
- `mise-tasks/metrics` — いま測れるものを TSV で出す。読むのは `ent` の出力だけにする
- ループ検知の二系統化と Actor の試行台帳 — この7つで効果を測る。M5 と M6 が主役になる
- **観測を足す2つの作業** — 判断の履歴を出す口（M6・M4）と、畳んだ理由に
  「早すぎた / 妥当だった」を持たせる欄（M7）。どちらも挙動を変えるので、別の作業になる
